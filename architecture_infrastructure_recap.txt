This document recaps our technical discussion regarding porting the code to Go, 
decoupling the LLM inference layer to handle high concurrency, and sourcing

--------------------------------------------------------------------------------
1. PORTING CODE TO GO: DIFFICULTY BREAKDOWN
--------------------------------------------------------------------------------
Porting the B2C/B2B business logic, databases, and APIs to Go is highly 
efficient, but native LLM weight loading must be handled externally.

- API Server (FastAPI -> Go net/http or Gin):
  * DIFFICULTY: Very Low
  * WHY: Go is designed for highly concurrent web routing and JSON bindings.

- Data Bank (SQLite3 -> Go database/sql + modernc.org/sqlite):
  * DIFFICULTY: Very Low
  * WHY: Pure Go drivers exist, removing the need for a CGO compiler.

- Memory System (Python maps/JSON -> Go maps/JSON):
  * DIFFICULTY: Very Low
  * WHY: Maps and standard JSON encoding handle context saving easily.

- Candidate Evaluator (Python prompts/JSON -> Go structs/formatting):
  * DIFFICULTY: Low
  * WHY: Formatting prompts and parsing LLM JSON responses with structs is simple.

- Model Loader & Inference (PyTorch/Transformers -> Go):
  * DIFFICULTY: High
  * WHY: No native Go equivalents exist for PyTorch, bitsandbytes (4-bit 
    quantization), and PEFT (LoRA). You must host inference on a separate service.

--------------------------------------------------------------------------------
2. PRODUCTION INFRASTRUCTURE: COMPARATIVE ANALYSIS
--------------------------------------------------------------------------------
To support hundreds or thousands of concurrent users, the application server (Go)
must be separated from the model runner. Below are the two decoupled options:

+--------------------+--------------------------------+------------------------+
| Criteria           | Serverless API (Managed)       | Self-Hosted Decoupled  |
|                    | (Gemini, OpenAI, Groq)         | (vLLM on GPU Instances)|
+--------------------+--------------------------------+------------------------+
| Best For           | Fast MVP, scaling, low ops,    | Custom fine-tuned SLM, |
|                    | variable traffic volumes.      | privacy, flat cost.    |
+--------------------+--------------------------------+------------------------+
| Operational Effort | None (standard API calls)      | High (Docker, CUDA)    |
+--------------------+--------------------------------+------------------------+
| Cost at 0 Users    | $0 (Pay per token used)        | Fixed monthly flat rate|
|                    |                                | (~$700+/mo minimum)    |
+--------------------+--------------------------------+------------------------+
| Model Control      | Limited to vendor base models  | 100% control over your |
|                    |                                | custom weights & QLoRA |
+--------------------+--------------------------------+------------------------+
| Data Privacy       | Data sent to third-parties     | Max security (VPC only)|
+--------------------+--------------------------------+------------------------+
| Inference Speed    | Ultra-fast (e.g. Groq 250 t/s) | Depends on rented GPU  |
+--------------------+--------------------------------+------------------------+
